# 处理过程

网页和 CLI 使用相同的 `Rewriter`，没有两套改写实现。

```text
TXT / Markdown
  → documents：按段拆分，保留空白和不改写的结构
  → model：请求本机 llama.cpp 的 /completion
  → guards：比较数字、引用、保护词等具体内容
  → pipeline：选首个通过规则的改写，失败时保留原文
  → 原文 / 改写稿 / 每次候选 / 错误 / 文本哈希

用户另行授权
  → detectors：外部检测或手工报告校验
  → 带时间、版本、来源标签和文本哈希的检测报告
```

## 为什么没有“自动改到通过”

改写与检测是两个独立动作。反复把论文发给外部检测器会增加费用和数据外传；检测分数降低，也可能只是内容被改坏。第一版只尝试有限候选，不根据外部检测分数循环改写。后续效果研究应在许可清晰的评测文本上单独进行。

## 错误如何处理

- 数值、引用等硬性差异：保存候选及原因，尝试下一个候选。都不合适时保留原文。
- 否定、确定性等变化：保留醒目的风险提示。即使没有提示，每份输出都要求复核。
- 段落生成截断或空输出：该段失败，后面的独立段落仍可处理。
- 服务失联或响应无效：停止继续请求，避免每段重复等待超时。
- 浏览器取消：等待实际连接断开，取消并回收后台任务；已经发给供应商的内容无法撤回。
- 输入被编辑：前端取消旧任务，丢弃旧响应、导出状态和检测授权。

## 本机边界

服务默认只监听 `127.0.0.1`，验证 Host 与 Origin，限制 JSON 大小。模型地址由启动配置决定且只能是 loopback 地址，不接受用户请求任意指定网址。模型与检测客户端均关闭代理继承和自动重定向。

没有账号系统、数据库或遥测。稿件不写入服务日志；用户主动导出的 JSON 则包含全文，需要按私人文件保管。这些设置适用于单人本机工具，不替代对恶意本机软件的防护，也不适合直接开放到公网。
